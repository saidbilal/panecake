# Panecake

A local macOS app that puts a Claude Desktop-style sidebar and grid around the real Claude Code CLI.

## Core decision

Each chat is the unmodified `claude` binary running in an embedded terminal (xterm.js + node-pty). Do not replace this with a custom chat UI over `--output-format stream-json`: that cannot run interactive TUI features such as `/config`, pickers and the status line. Embedding the real TUI also means CLI updates need no work here.

## Layout

| Path | Job |
| --- | --- |
| `server.mjs` | Indexes transcripts, runs `claude` and shells in PTYs, serves the UI and API |
| `public/app.js` | Sidebar, grid, terminals, Cmd+click links, Markdown preview (no framework) |
| `public/style.css`, `public/index.html` | Interface |
| `public/vendor/` | Generated by `scripts/vendor.mjs`; gitignored |
| `CHANGELOG.md`, `scripts/notes.mjs` | Release notes, one `## x.y.z` section per release; the parser the server and `/release` share |
| `.claude/skills/release/` | The `/release` skill: notes, preview, version, tag, GitHub release |
| `mac/main.swift`, `mac/build.sh` | Native WKWebView shell; builds `~/Applications/Panecake.app` |

## Commands

- `npm run setup`: install dependencies with scripts disabled, copy vendor files, restore the execute bit on node-pty's `spawn-helper`
- `npm run build`: setup, then build the app
- `npm start`: run only the server; prints the local URL with its token
- `npm run preview-notes`: open the What's New popup for `package.json`'s version in the browser, on throwaway settings
- `/release`: cut a release; it previews the notes and waits for approval before anything is pushed

Changes to `server.mjs` or `public/` need only an app restart. Rebuild only after changing `mac/` or moving this folder. Rebuilding writes to `~/Applications`, which can trigger a macOS "modifying apps" prompt.

## Rules

- Never write inside `~/.claude` or Claude Desktop's data. Panecake only reads them. Renames, hides and preferences go in `~/Library/Application Support/Panecake/`.
- Never run a recursive delete on a computed path, especially near `~/.claude/projects`. An empty variable there would wipe all chat history.
- The server can type into shell-capable processes. Keep it on 127.0.0.1 and keep the per-launch token, Host check and exact WebSocket Origin check.
- Terminal output and Markdown files are untrusted. A click must never launch anything: `/api/reveal` only opens plain folders and selects everything else in Finder, including bundles like `Foo.app`.
- Markdown previews go through DOMPurify and make no network requests, so remote images become links. Run `npm audit` after changing dependencies, because the sanitizer is a security boundary.
- Never send the user's personal information to outside services.

## Behavior that looks odd but is deliberate

- **Finding a chat's folder:** resuming needs the chat's original folder, and later `cwd` values in a transcript can differ. `parseSession` picks the `cwd` that encodes to the transcript's folder name. When a project folder was moved and its transcript folder renamed to match, the transcripts still record the old path; `rowCwd` then finds the new folder (from newer chats in that transcript folder, the same move seen elsewhere, or a renamed folder next to the old one) and accepts it only if it exists and encodes to the folder name.
- **Reading transcripts:** only the first and last 128 KB are read normally. A pasted screenshot can push the first message past that, so people's chats get a longer read of up to 16 MB. Raise `INDEX_VERSION` whenever parsing changes.
- **Titles:** Claude Code writes its own automatic title into each transcript as `ai-title` records and rewrites them as the chat goes on; the newest wins. Priority: a Panecake rename, `/rename` (`custom-title`), a title the user chose in Desktop, `ai-title`, Desktop's automatic title, then the first real prompt. Pasted-text tags are stripped, and bare commands such as `/model` or `/clear clear` never become a title.
- **Live state:** `~/.claude/sessions/<pid>.json` supplies busy, idle and waiting status, and the current session ID, which changes on `/clear` and `/resume`.
- **Rendering:** use xterm's DOM renderer. The WebGL addon rendered a blank terminal in testing.
- **Dragging:** the grid uses mouse events rather than HTML5 drag and drop, so it behaves the same in Chrome and WKWebView and can be tested in both.
- **Cmd+click:** the fullscreen TUI turns on mouse tracking, so Panecake finds the text under the pointer itself and intercepts the click before xterm sees it. Do not rely on xterm's link providers for this.
- **Find (Cmd+F):** terminals use `@xterm/addon-search`, which covers scrollback. A chat's fullscreen TUI keeps its own history, so there only the visible screen is searchable. Markdown previews use the CSS Custom Highlight API, so the page itself is never modified. The add-on ignores option changes until `clearDecorations()` is called, which is why the case toggle calls it.
- **Option key:** it does not act as Alt by default, because Turkish, German and other non-US layouts need it to type characters like `@` and `#`. Find folds case one character at a time so Turkish `İ` keeps match positions aligned.
- **Status marks:** spinners are only for chats, which finish on their own. A terminal running a program gets a static green dot, since a dev server can run indefinitely.
- **Sidebar columns:** carets and status dots stay in fixed columns so running chats can be scanned at a glance.
- **Tabs:** each tab is its own split tree, and a chat or terminal lives in at most one pane across all tabs, so placing it somewhere moves it. Chats in a background tab start their process only when the tab is first shown (`lazy` panes), and only the tab on screen counts as visible to the server, so idle chats in other tabs can be evicted and resume when shown. A tab emptied by moving its content out is removed. A tab dropped on the middle of another tab merges into it (near a tab's edge it reorders instead); once a held drag opens the other tab, it can also be dropped on a pane's edge. Clicking a chat or terminal that no tab shows opens it in a new tab (or the tab on screen when that is empty), so nothing replaces what a tab already holds; ⌘⌥↑/↓ reuses the tab its previous step opened until something is typed there. Closing a tab never stops a process, but a process that ends removes its pane and, if that empties the tab, the tab. The sidebar does not mark rows that are open in some tab; the pane flash shows where a click went. With one tab the strip is hidden and floats in over the grid only during a drag.
- **Updates:** the server asks GitHub's `releases/latest` for `saidbilal/panecake` at launch and every 12 hours, with only a generic User-Agent. The reply is untrusted: only a plain `x.y.z` tag is kept, and the release link is built locally. The Update button opens a shell in this folder with `git pull --ff-only && npm run build` typed but not run. A release is a `vX.Y.Z` tag matching `package.json`'s version, a `## X.Y.Z` section in `CHANGELOG.md` and a GitHub release; `/release` makes all of them.
- **What's New:** the server keeps `seenVersion` in its state file. When the running version is newer, the page shows the `CHANGELOG.md` sections in between in a popup (only the current one when nothing was recorded, as for people coming from 0.2.0), and closing it records the version. A new install records its version at once and shows nothing. The notes are Markdown through DOMPurify with images removed; links open in the browser. While the popup is up it swallows keys, so nothing is typed into the chat behind it. `PANECAKE_WHATS_NEW=1` shows the popup on every load and records nothing; that is the release preview.
- **Rebuilds are skipped when nothing changed:** the app is signed ad hoc, so macOS treats each rebuild as a new app and asks for its permissions again. `mac/build.sh` stores a hash of its inputs in the bundle and exits early when it matches; `--force` rebuilds anyway. Keep changing values such as the version out of Info.plist, or every release would re-sign the app.
- **Themes:** Dark (default), Light, or Match macOS. CSS colors are tokens on `:root`, overridden under `[data-theme="light"]`; terminals get `TERM_THEMES`. Claude Code has its own palette, so a chat starts with `--settings {"theme":"light"|"dark"}` when the user's `~/.claude/settings.json` theme is in the other family. That flag changes only that run. Running chats keep their colors until reopened. The page sends `theme:light|dark` to the native shell, which sets the window's appearance and remembers it for the next launch.
- **Sidebar order:** with last activity chosen, projects come first by recent activity. Opening a chat resumes it, which appends to its transcript and so counts as activity. The sort button in the "Chats" heading (`sortBy`) orders chats and projects by creation (the default) or by last activity. Versions before 0.4.0 saved `sortBy: 'active'` with every settings change, so `sortCreatedDefault` in the state file marks the one-time switch of everyone to creation. Creation uses the transcript file's birth time (for a fork, the time it was forked), and rows then show the created time. Home and then the closed Issues section sit below a divider at the bottom, and each `issue-N` folder is its own group inside Issues.
- **Pins:** `pinned` in the state file is the user's ordered list of chat IDs. Pinned chats render in their own section above the heading that carries the sort button, are left out of their project group, and ignore the sort. A pinned chat is listed even when it or its project is hidden or it is an automated run; hiding one unpins it and pinning one unhides it. IDs with no transcript are kept, because the list can be saved while indexing is still running. Dragging any chat over the Pinned section pins or reorders it (`pinDropAt`); everywhere else the drag goes to the grid as before. `pinnedProjects` is the ordered list of pinned project folders, shown as whole groups below the pinned chats and left out of the normal list (including Home and Issues). A chat pinned on its own stays in the chat list above even when its project is pinned too. Hiding a project unpins it and pinning one unhides it; a pinned project keeps its heading even when every chat in it is pinned on its own.

## Testing

- Set `PANECAKE_DATA_DIR` to a throwaway folder so tests do not touch real preferences, and `PANECAKE_NO_UPDATE_CHECK=1` so they make no request to GitHub. To test the Update button, point `PANECAKE_UPDATE_FEED` at a local server that returns `{"tag_name":"v9.9.9"}`.
- Drive the UI with `playwright-core` and installed Chrome, using real mouse input.
- Use throwaway chats in temp folders, never the user's real chats. Resuming writes to a transcript.
- Set `ANTHROPIC_MODEL` to a small model when a test sends messages. Do not use `/model`, which can change the user's settings. `!command` in the TUI can still trigger a model reply.
- Mock `/api/reveal` and `/api/open-url` in tests so windows do not open on the user's screen.
- Chrome is not WebKit. Check UI changes in a temporary copy of `mac/main.swift` too, using `WKWebView.takeSnapshot`, because Terminal has no Screen Recording permission for `screencapture`.
- A WKWebView probe window behind other windows reports `document.visibilityState` as hidden, and WebKit pauses drawing. Call `window.orderFrontRegardless()` before judging what it renders.
- Look at screenshots as well as assertions. They have caught bugs that passing checks missed.
- Test chats must not live under `/tmp`: the sidebar treats those folders as automated runs and hides them. Point `HOME` at a throwaway folder holding small transcripts whose `cwd` is somewhere else.
- To test What's New, start with a state file that has no `seenVersion` (an existing user) or an older one, and a matching section in `CHANGELOG.md`. A missing state file is a new install and shows nothing.
- For a chat that costs nothing, put an executable stub at `$HOME/.local/bin/claude` in the throwaway home (for example a script that prints its arguments and runs `cat`); the server prefers that path.
- A test that crashes can leave its server and PTYs running. The user's own app runs the same `server.mjs`, so check the PID before stopping anything.
